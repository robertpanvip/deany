# 类型擦除—恢复压测报告

> 日期：2026-11-18。方法：拉取真实开源 TS 项目 → 把显式类型注解擦成 `any` → 用 `deany infer-any` 从使用证据恢复 → 逐个对照原始类型。
> 初测仅评估工具恢复能力；随后针对发现的字符串语境缺口做了小范围修复并复测（见第三、四节）。

## 一、测试样本

拉取 9 个候选开源库，其中 3 个新版本源码已是 JS + 类型测试（无可擦除的实现类型），最终选取有真实函数体 TS 实现的库：

| 库 | 来源 | 用于测试的文件 | 特点 |
|---|---|---|---|
| p-queue | `sindresorhus/p-queue` | `source/lower-bound.ts`、`source/priority-queue.ts`、`source/index.ts` | 注解密集（index.ts 有 82 处），泛型 + 具体类型混合 |
| mitt | `developit/mitt` | `src/index.ts` | 泛型密集型（`Events[Key]`/`keyof`），对 usage 推断是硬骨头 |

## 二、测试结果（逐槽位单独擦除，精确对照）

只评估"具体可对照"的类型注解，跳过纯泛型参数/类型运算（那些的值证据在类型层，擦成 any 本就无从恢复，不算工具能力问题）。

| 类别 | 数量 | 占比 |
|---|---|---|
| ✅ 精确恢复（恢复成原类型） | 9 | 41% |
| ~ 变成其它具体类型（多为等价/更宽泛） | 4 | 18% |
| ✗ 仍是 `any` | 9 | 41% |

> 上表为**修复后**复测数据；修复前为 8 / 4 / 10（36% / 18% / 45%），对照见第四节。
| ❌ 异常 | 0 | 0% |
| **合计** | **22** | |

### 成功恢复的典型（有明确值证据）

| 位置 | 原始 | 恢复证据 |
|---|---|---|
| `lower-bound.ts` 返回 | `number` | `return first`，`first = 0` 算术演化 |
| `priority-queue.ts #findIndex` 返回 | `number` | `return index`，`index` 来自数值查找 |
| 多个 `void` 方法返回 | `void` | 函数体裸 `return` / 无值返回 |
| mitt `on/off/emit` 的 `Key` 参数 | `Key` | 实现体内 `all.get(type)` 的上下文类型 |

### 未恢复的 10 项分类

| 分类 | 例子 | 性质 |
|---|---|---|
| **重载签名声明**（无函数体） | `remove(id: string): void`、`remove(run): void` | **固有局限**：无函数体即无使用证据，无法恢复 |
| **泛型键参数** | mitt 的 `on(type: Key)`、`'*'` | **固有局限**：类型信息在 `keyof Events` 约束里，值层无具体证据 |
| **实现体函数返回** | `setPriority(): void`（体内有裸 return 但被重载遮蔽） | 边界情况 |
| **字符串语境参数** | `setPriority(id: string)`（用于 `` `${id}` `` / `===`）、`priority: number`（用于数值比较） | **真实能力缺口**：见下 |

## 三、字符串语境缺口：已修复并复测

初测发现参数只出现在字符串语境时停在 `any`。三类语境都是真实的值层使用证据，已补入 `constraintsFromReference`，并在 `mergeEvidence` 中作为**弱兜底来源**：

| 语境 | 例子 | 修复后结果 |
|---|---|---|
| 模板插值 | `` `id is ${id}` `` | `id: string` ✅ |
| 字符串 `+` 拼接 | `'x' + a` / `a + 'x'` | `a: string` ✅ |
| `===` / `!==` 字符串字面量 | `id === 'x'` | `id: string` ✅ |
| 成员访问（原有基线） | `a.length` | `{ length: unknown }` ✅（不变） |

**关键安全设计**：这三类语境只能证明"该值可用于字符串语境"，不能证明"一定是 string"（插值与 `+` 也接受 number）。因此它们不是协变 source，而是 `Evidence.stringContext` 弱提示：

- 只在**没有任何强证据**时兜底为 `string`，且结果标记为 weak，fixed-point 后续轮次发现更具体来源时会覆盖；
- `function f(a: any) { return a + 1; }` → `a: number`，数值证据优先，未被污染；
- p-queue `index.ts` 的 `setPriority(id, priority)` 中，`priority` 虽出现在 `` `${priority}` `` 插值里，但另有 `typeof priority !== 'number'` 的强证据，仍正确恢复为 `number`，**没有被误推成 string**。

## 四、修复前后对照（22 槽位逐槽位单独测）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 精确恢复 | 8（36%） | **9（41%）** |
| 变成其它具体类型 | 4（18%） | 4（18%） |
| 仍是 `any` | 10（45%） | **9（41%）** |
| 异常 | 0 | 0 |

唯一变化项：`priority-queue.ts L92 setPriority(id: string)`，从 `✗ any` 变为 `✓ string`。其余 9 个 `any` 仍是重载签名（无函数体）与 `keyof Events` 泛型键——类型信息在类型层，值层无证据，属于固有局限，未做臆测。

验证：新增 3 个单元测试（三类字符串语境、不覆盖数值证据、不臆测 case），全量 **149/149** 通过，`typecheck` 通过。

## 五、结论

1. **有明确值证据时恢复能力强**：初始化器、算术、返回表达式、成员访问、上下文类型、字符串语境都能恢复。
2. **恢复不了的仍是"本来就没证据"**：重载签名、泛型键、纯类型声明——这是保守设计的正确表现，不是缺陷。
3. **字符串语境是弱证据**：只在无强证据时兜底，不会把 `number` 参数误推成 `string`，符合"宁可留 `any` 也不臆测"的既定原则。
